The Mint Motive API

Three APIs on one engine. The Engine API turns settings into print-ready models, 77 kinds of them (Gridfinity bins and baseplates, Skådis, Deck Foundry, server racks, kitchen, desk and home organisers and more, every one listed under Kinds and settings), as STL, 3MF or OBJ. The Tracer API turns a photo of tools on a sheet of paper into outlines in millimetres, or a finished bin with a pocket for every tool. The Print AI API checks a print before slicing, after slicing and from a photo after printing, and gives the exact settings to change.

Base URL

https://api.mintmotive.com.au

Format

JSON in, files or JSON out

Every path below is relative to the base URL. The same API also answers under /api, so /engine/v1/generate is also /api/engine/v1/generate.

Authentication

Send your key on every call, in the Authorization header:

Authorization: Bearer vx_YOUR_KEY
KeyForWhere it comes from
vx_…Engine APIYou make it in the console, up to five live keys per account.
tk_…Tracer APIIssued by us to partners, with a monthly photo allowance and a price per photo. Test keys work before launch and are never billed.
  • Keep keys secret. Use them from a server, never in a web page or an app someone can unpack.
  • One key per use (a shop, a bot, a script), so you can see each one's calls and revoke one without stopping the rest.
  • Revoke a key in the console and it stops working at once. Its past calls stay in your log, under its name.
  • Test keys (vx_test_…, tick "Test key" when you make one): every call is checked exactly like a real one, but files come back as a 20 mm test cube (header X-Mint-Test: 1), photo diagnosis returns a fixed sample report, and nothing counts against your plan. They work even while an API is switched off. Two per account, 20 calls a minute.
  • Team keys: start a team in the console (Team), invite people by handle or email, and make keys for the team. They run on the team owner's plan and count toward the owner's keys. Owners and admins make, lock, limit and revoke them; members see them and their calls. Closing a team revokes its keys.
  • Lock a key to your server's addresses and a leaked copy is useless anywhere else. See Locking a key.
  • We only ever store a fingerprint of your key, plus its first few characters (like vx_ab12…) so you can tell keys apart.

Requests and responses

Send JSON with Content-Type: application/json, except a tracer photo, which can be the raw image. Successful calls answer with a file or with JSON. Every answer carries these headers:

HeaderWhat it is
X-Request-IdThis call's id, like req_8KQe2f…. On every answer, errors too. Quote it when you ask for help.
X-Vertex-SerialThe serial number stamped into the file, like VX-2610-8K2F-QP7D. On every file.
X-Vertex-EngineThe engine version that made the file.
X-Vertex-PartsThe parts in the file, comma separated.

An error is JSON with one plain sentence that says what went wrong and how to fix it:

{ "error": "gridX is at most 10." }

Custom generators

Make your own generator out of our engine's parts, without running any code of your own. A generator is a recipe. It has inputs (numbers with a range, choices, or on/off switches) and parts. Each part is one of the kinds from GET /engine/v1/kinds, with its settings, a place (at, in mm) and a turn (rotate, in degrees about x, y and z).

  • A setting can be written as is ("gridY": 1), name an input ("gridX": "$count"), or be a formula ("heightUnits": "=3 + $tall * 3"). Formulas take numbers, inputs, + - * /, brackets and min max round floor ceil abs clamp. Nothing else runs. An on/off input counts as 1 or 0.
  • when switches a part on or off ("when": "$withLid"). repeat: { count, step: [x, y, z] } makes a row of copies.
  • Limits: 24 inputs, 24 parts, 48 pieces once repeated, 2 million triangles, 32 KB, and 50 generators per account.
{
  "name": "Bin row",
  "inputs": [
    { "id": "count", "type": "number", "min": 1, "max": 4, "default": 2 },
    { "id": "tall", "type": "bool", "default": false }
  ],
  "parts": [
    { "kind": "baseplate", "name": "plate", "params": { "gridX": "$count", "gridY": 1 } },
    { "kind": "bin", "name": "bin", "params": { "gridX": 1, "heightUnits": "=3 + $tall * 3" },
      "at": [0, 0, 5], "repeat": { "count": "$count", "step": [42, 0, 0] } }
  ]
}

The check, and Verified

Every save is checked on our reference engine. It runs the defaults, every number at its smallest and largest, every choice and every switch. It reports parts that are broken (refused or empty), off-spec (below the bed), and settings or parts that change nothing (not a setting of that kind, always the kind's default, the same part twice, or an input nothing uses). You get a match score. A generator scoring 95% or more, with nothing broken or off-spec, is Verified. Make and check them in your console, or with POST /engine/v1/custom/check (your key, or signed in; this never counts as a call).

Using one

POST /engine/v1/custom/:id/generate with { "inputs": { … }, "format": "3mf" } answers with the file, just like /generate, on your plan's allowance. Inputs are kept inside their ranges. X-Vertex-Verified says whether it passed the check. Your own generators work for you; once published, anyone's key can use them. GET /engine/v1/custom lists yours and the published ones, and GET /engine/v1/custom/:id gives one's inputs.

curl -X POST https://api.mintmotive.com.au/engine/v1/custom/cg_AbC123xy/generate \
  -H "Authorization: Bearer $MINT_KEY" -H "Content-Type: application/json" \
  -d '{ "inputs": { "count": 3, "tall": true }, "format": "3mf" }' -o bin-row.3mf

How tracing works By invitation

Lay tools on a sheet of paper and photograph them from above. The paper is the ruler: we find its corners, straighten the photo, and measure every tool in millimetres.

1

POST /trace/v1/jobs
Send the photo. You get a job id at once.

2

GET /trace/v1/jobs/:id
Check every second or two until it's done (usually a few seconds).

3

Use the outlines, or GET …/bin for a ready bin with a pocket per tool.

Photos are traced and thrown away; jobs are kept for 15 minutes. A photo that fails costs nothing from your allowance, and is never billed.

Billing per photo. Your agreement sets a price per photo and how many photos each month are free. Only photos that traced count. Each month's total goes on your account's next invoice as one line. GET /trace/v1 shows your price and what this month owes so far. Test keys are never billed.

GET /trace/v1

Your key's name, whether it's a test key, this month's allowance and use, and (for a live key) its price and what this month owes so far, in cents.

Taking good photos

  • Straight from above, with the whole sheet in view and a little table round it.
  • A darker surface than the paper, so its edges stand out.
  • Even light: daylight or two lamps. Avoid a single hard light that throws long shadows.
  • Tools flat and apart, not touching each other or the edge of the sheet.
  • Shiny steel: tilt the light a little to kill glare.

How Print AI works New

Print AI checks a 3D print at every step and says exactly what to change. It checks the model before slicing (overhangs, bridges, bed contact, a closed mesh, the best way up), the slicer settings after slicing (temperatures, layers, cooling and retraction for your filament and nozzle), and a photo after printing (Print Doctor names the fault, boxes it on the photo and gives the settings that fix it).

Your developer key (vx_…) works here, on your plan's allowance. GET /ai/v1 says what's ready; GET /ai/v1/filaments lists each filament family's safe ranges. Neither needs a key.

The VERTEX slicer plugin (OrcaSlicer, Bambu Studio and PrusaSlicer post-processing) runs the settings checks on your computer for free, and sends the settings (never your model) here when you set VERTEX_API_KEY.

POST /ai/v1/check/settings

Slicer settings against safe ranges. Send any of these:

  • JSON: { "settings": { "filament_type": "PETG", "nozzle_temperature": 275, … }, "context": { "nozzle": 0.4 } }. Setting names are your slicer's own; OrcaSlicer, Bambu Studio and PrusaSlicer names all work.
  • G-code as the body (text/plain, up to 200 MB). The settings comments the slicer writes are read; the moves are skipped.
  • A sliced 3MF as the body (model/3mf).

With a file as the body, give the context on the query string: ?filament=PETG&nozzle=0.4.

curl -X POST "https://api.mintmotive.com.au/ai/v1/check/settings?filament=PETG" \
  -H "Authorization: Bearer $MINT_KEY" \
  -H "Content-Type: text/plain" \
  --data-binary @part.gcode

POST /ai/v1/check/model

A model before slicing. Send an STL or 3MF as the body (up to 50 MB), or { "kind", "params" } to check any Engine API model. You get its size, volume, whether the mesh is closed, how much overhangs and bridges over air, how much sits on the bed, and the six flat ways it could lie, with the best one.

QueryDefaultWhat it is

POST /ai/v1/diagnose/photo

Print Doctor. Send a photo of a finished or failed print as the body (JPEG, PNG, WebP or HEIC, up to 12 MB), or { "image": base64, "context": { … }, "settings": { … }, "share": false }. Each finding names the fault (spaghetti, warping, stringing, under-extrusion, layer shift, poor first layer, elephant's foot, ringing and more), boxes it on the photo as fractions of the image ([x, y, w, h]), and gives the settings to change. Tell it the filament and printer for sharper answers. Photos are looked at and thrown away, unless you send share: true to help Print Doctor learn. 6 photos a minute and 200 a day per key.

POST /ai/v1/outcomes

Tell us how the print went, so the checks learn which fixes work: { "job": "your-id", "result": "good" | "failed" | "fixed", "finding": "warping", "fixedBy": "bed_temperature:105", "note": "…" }. Answers 202.

POST /ai/v1/watch/frame?job=…: live failure watch

Send a frame from the printer's camera every 20 seconds or so while it prints (the body is the JPEG or PNG; job is your own id for the print, the same on every frame). You get back action: continue, check (something's worth a look) or pause. It only says pause when two frames in a row show a print-ending fault: spaghetti, a layer shift, a clog or layers splitting. One blurry frame never stops a print. You also get message, fault, streak and the same findings as a photo diagnosis. One frame every 20 seconds per job; frames count toward the photo allowance.

curl -X POST "https://api.mintmotive.com.au/ai/v1/watch/frame?job=benchy-42" \
  -H "Authorization: Bearer $MINT_KEY" -H "Content-Type: image/jpeg" \
  --data-binary @frame.jpg
# → { "action": "check", "message": "Keep an eye on it: …", "fault": "spaghetti", "streak": 1, … }

POST /ai/v1/apply

Write fixes into your settings file. Send the file as the body: a PrusaSlicer .ini, a Bambu Studio or OrcaSlicer .json preset, or a .3mf project. Add ?name= (its file name, so we know the format) and ?fixes=, a JSON list of { "setting", "to" } straight from a check's findings. You get the same file back with the fixes written in, in each slicer's own setting names. The X-Fixes-Applied header lists what changed, and X-Fixes-Missing lists what isn't in the file. GET /ai/v1 lists the settings that can be fixed under fixable. G-code is already sliced: fix the profile and slice again.

curl -X POST "https://api.mintmotive.com.au/ai/v1/apply?name=profile.ini&fixes=%5B%7B%22setting%22%3A%22nozzle_temperature%22%2C%22to%22%3A215%7D%5D" \
  -H "Authorization: Bearer $MINT_KEY" --data-binary @profile.ini -o profile-fixed.ini

GET /ai/v1/recipes and POST /ai/v1/recipes/:id/apply: your VERTEX Recipes

GET /ai/v1/recipes lists your own Recipes on VERTEX (id, title, fileName, verified). POST /ai/v1/recipes/:id/apply works like /apply, and the fixed file then replaces that Recipe's profile. It only reaches the Recipes of the account that owns the key. The new file goes through the usual safety checks, and a verified Recipe is checked again before it shows as verified. If none of the fixes are in the file, the Recipe is left as it was (400). Test keys can't change Recipes. Profiles can be up to 20 MB.

{ "applied": ["nozzle_temperature"], "missing": [], "recipe": { "id": "k3Jd9sQe", "title": "PETG on the P1S", "url": "/recipes/k3Jd9sQe", "fileName": "profile-fixed.ini" }, "held": false }

Findings and fixes

Every check answers { findings, model, summary }. model names the checker version (e.g. settings-0.2.0), so you can tell when the rules changed.

codeWhat was found, e.g. temp-high-for-filament, layer-too-tall, steep-overhangs, warping. Stable: build on it.

Limits, plans and quotas

Your account's plan sets the engine API's limits. The day's allowance belongs to your account and is shared by all your keys: more keys never means more calls. The per-minute limit is per key, so one busy script can't use it all up. The plans and prices are on the overview, and you can change plan in the console at any time.

Each key's own limits. In the console, give any key its own cap on calls a day and on extra use a month (in dollars, past your plan's daily allowance). A key at its cap gets a 429 that says which cap it hit; your other keys carry on. They sit on top of your account's limits, never above them.

Locking a key to your servers

In the console, press Lock on a key and list the addresses it may be used from: single IPs (IPv4 or IPv6), or IPv4 ranges like 203.0.113.0/24, up to 20. From anywhere else the key answers 403, even with the right key. Leave the list empty to let the key work from anywhere again.

Lock keys that run on servers with fixed addresses. Don't lock a key used from a laptop or a home connection whose address changes.

  "id": "evt_8sKq2mZ0aB1c",
  "type": "usage.80",
  "created": 1790000000,
  "data": { "key": { "id": 12, "name": "Shop orders", "hint": "vx_ab12…" }, "used": 800, "limit": 1000, "window": "24h" }

HeaderHolds
Mint-Signaturet=<unix seconds>,v1=<hex HMAC-SHA256> of <t>.<raw body>, keyed with your secret.
Mint-EventThe event type.
Mint-DeliveryThe event id. The same id comes again on a retry, so you can skip repeats.

Check every signature before trusting a delivery, and refuse ones more than five minutes old:

import crypto from "node:crypto";

// rawBody: the request body exactly as it arrived, before JSON.parse.
function verify(rawBody, header, secret) {
  const parts = Object.fromEntries(header.split(",").map((p) => p.split("=")));
  const expected = crypto.createHmac("sha256", secret).update(`${parts.t}.${rawBody}`).digest("hex");
  const got = Buffer.from(parts.v1 || ""), want = Buffer.from(expected);
  const fresh = Math.abs(Date.now() / 1000 - Number(parts.t)) < 300;
  return fresh && got.length === want.length && crypto.timingSafeEqual(got, want);
}

Request ids and serials

Everything you make can be traced, by you and by us:

  • Every call gets a request id (X-Request-Id), errors included.
  • Every file carries a serial number (X-Vertex-Serial), stamped into the file. It records when and how the file was made, and nothing about you.
  • Your console lists every call your keys made: when, the endpoint, what you asked for, the result, how long it took, the serial and the request id. Search it by request id, serial or path.
  • We watch for trouble around the clock: sudden spikes, keys that keep failing, key guessing and scraping. If something looks wrong with your key we may get in touch, or block an address while we look.
  • Delete your VERTEX account and the account, IP address, client and settings on your calls are wiped from the log; only anonymous counts stay.
  • We keep the call log for two years, to answer support questions, spot abuse and keep the service healthy. It holds the key used, the account, the IP address and the client's user agent, never the key itself.
